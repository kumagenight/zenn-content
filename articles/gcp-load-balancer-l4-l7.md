## はじめに

GCPのロードバランサ（LB）は種類が多く、「外部HTTPS」「SSLプロキシ」「TCPプロキシ」「TCP/UDPネットワーク」…と名前を見ても、どれを選べばいいのか最初はまったく分かりませんでした。

でも、**たった2つの軸**で整理すると一気に見通しが良くなります。

1. **L4 か L7 か**（どの深さまで中身を見るか）
2. **プロキシ か パススルー か**（接続を終端するか、素通しするか）

この記事では、この2軸を土台に、各LBが「何を・どこまでやる人なのか」を体系的に整理します。GCP Associate Cloud Engineer（ACE）の試験対策にもなるよう、最後に**選び方フロー**と**キーワードのひも付け**も載せます。

:::message
本記事は「中身を読んで賢く振り分けられるのはHTTP(L7)だけ」という一点を軸に構成しています。ここが腹落ちすると、全部つながります。
:::

## 前提：TCP / UDP / HTTP / HTTPS の関係

LBの話に入る前に、土台の用語を整理します。ここが曖昧だと必ず混乱します。

### TCP と UDP は「運び方」の2方式

| | TCP | UDP |
|---|---|---|
| 例え | 書留・宅配便（受領確認あり） | はがき・拡声器（出しっぱなし） |
| 到達確認 | する（届かなければ再送） | しない |
| 順番保証 | する | しない |
| 速さ | やや遅い | 速い・軽い |
| 用途 | Web・メール・DB など欠けたら困るもの | 動画・通話・ゲーム・DNS など速度命 |

### HTTP と HTTPS はレイヤが違う

ここが最初の落とし穴です。「HTTPS か TCP か」という比較は**そもそも土俵が違います**。

```
L7（アプリ）   HTTP        ← 何を話すか（Webの中身）
（暗号化層）   TLS/SSL     ← 暗号化する層（オプション）
L4（運搬）     TCP         ← どう運ぶか
```

組み合わせるとこうなります。

```
http://   = HTTP            over TCP   （暗号化なし）
https://  = HTTP + TLS暗号化  over TCP   （暗号化あり）
```

つまり **HTTPS も土台は TCP**。「HTTPS vs TCP」ではなく「**TCPの上にTLSを載せたのがHTTPS**」です。

> 例え：**TCP = トラック**、**TLS = 鍵付き金庫**、**HTTP = 中の手紙**。
> HTTPS は「鍵付き金庫に入れた手紙をトラックで運ぶ」。トラック(TCP)は暗号化してもしなくても使う。

## 軸1：プロキシ と パススルー

LBを理解する一番の幹がこれです。

- **プロキシ（proxy）= 代理人**。クライアントとの接続を一度**終端（terminate）**して、自分が代理で別の接続を張り直す。接続が**2本**に分かれる。
- **パススルー（passthrough）**。接続を終端せず、**そのまま素通し**する。

```
プロキシ：    [クライアント] ──接続A──> [LB] ──接続B──> [backend]
パススルー：  [クライアント] ─────────素通し─────────> [backend]
```

この違いが、後で効いてきます。

| | プロキシ | パススルー |
|---|---|---|
| 接続 | 2本に分割（終端する） | 1本を素通し（終端しない） |
| backendから見た送信元IP | LBのIP（実IPは X-Forwarded-For 等で伝達） | **クライアントの実IPがそのまま** |
| TLS終端 | できる | できない |
| 戻り通信 | LB経由 | LBを経由せず backend→クライアント直接（DSR） |

:::message
**なぜパススルーは実クライアントIPが残るのか？**
封筒を開けて入れ直さない＝差出人（送信元IP）が書き換わらないから。「実クライアントIPを保持したい」が要件なら**パススルー一択**になります。
:::

## 軸2：L4 と L7（どの深さまで中身を見るか）

ネットワークのデータは封筒が入れ子になっています（カプセル化）。

```
[ L2 [ L3 [ L4 [ L7アプリデータ ] ] ] ]
  ↑外側                      ↑内側（中身）
```

- **L4 LB**：L3/L4 の宛先情報（IPアドレス・ポート）だけ見て、どのbackendへ流すか決める。**L7の中身（HTTPのURL等）は読まない**。
- **L7 LB**：一番内側のアプリデータ（HTTPのURL・ヘッダ）まで開けて読む。だから**中身に応じた賢い振り分け**ができる。

### 「中身を読んで振り分け」はHTTPの特権

ここが本記事のキモです。L7で中身を読んで振り分けるには、LBが**「そのプロトコルの文法を理解する通訳（パーサー）」**を持っている必要があります。

```
GET /api/users HTTP/1.1     ← HTTPには「ここがパス」という
Host: example.com              世界共通の決まった形式がある → 振り分けできる
```

そして **GCPのLBが積んでいる通訳は実質「HTTP用」だけ**。だから：

- **HTTP / HTTPS / gRPC**（gRPCはHTTP/2の上で動く）→ 中身で振り分け**できる**
- **HTTP以外の独自プロトコル** → 復号できても「どこがパスか」分からない → 中身で振り分け**できない**

:::message alert
「内容を読んでの振り分け（パス/ホストでルーティング）」ができるのは **HTTP(L7) だけ**。これ以降の話は全部ここに帰着します。
:::

## 各ロードバランサを「3つの動作」で分解する

混乱を防ぐ最大のコツは、LBの仕事を**3つの動作に分けて**考えることです。

1. **接続を終端する**（受け切って張り直す）
2. **TLSを開封する**（復号する）
3. **中身を読んで振り分ける**（URL/パス/ホストで）

この3つの「やる/やらない」で、各LBがきれいに整列します。

| LB | ① 接続終端 | ② TLS開封 | ③ 中身で振り分け | レイヤ |
|---|:---:|:---:|:---:|:---:|
| 外部HTTPS（Application LB） | ✅ | ✅ | ✅ | L7 |
| 外部SSLプロキシ | ✅ | ✅ | ❌ | L4 |
| 外部TCPプロキシ | ✅ | ❌ | ❌ | L4 |
| 外部TCP/UDPネットワーク（パススルー） | ❌ | ❌ | ❌ | L4 |

**上から下へ、機能が1つずつ減っていく**のがポイントです。

### 外部HTTPS（Application LB / L7）

3つの動作を**すべてやる**唯一のLB。TLSを復号して、中のHTTP（URL・パス・ヘッダ）を読んで振り分けます。

- `/api/*` → APIサーバー、`/images/*` → 画像サーバー、のようなパス振り分け
- TLS終端（証明書をLBで一元管理、Googleマネージド証明書で自動更新）
- Cloud CDN・Cloud Armor（WAF）連携
- カナリアリリース（重み付け振り分け）

### 外部SSLプロキシ（L4）

**HTTP以外**の暗号化されたTCP通信を受け、LBで**TLS終端（復号）はする**。でも**中身では振り分けない**。

中身がHTTPじゃないので、復号しても「どこがパスか」という基準がないからです。仕事は「暗号を玄関で解いてbackendのCPU負担を減らす」「証明書をLBに一元化する」「グローバルに分散する」まで。

> 例え：金庫（TLS）は開けるけど、中の手紙は読めない言語なので、**空いてる窓口へ案内するだけ**の受付係。

### 外部TCPプロキシ（L4）

暗号化を扱わず（TLS終端しない）、**接続を終端して張り直すだけ**。中身も読まない。

「じゃあ何のため？」→ **接続レベルの利点**です。backendをグローバル分散して近い/空きリージョンへ振る、接続の効率化、DDoS吸収（Cloud Armor連携）。

### 外部TCP/UDPネットワーク（パススルー / L4）

唯一の**パススルー**。終端せず素通しする。

- **実クライアントIPが保持される**
- **唯一 UDP を扱える**（プロキシ2種はTCP専用。UDPには終端すべき「接続」がないため）
- TLS終端もパス振り分けもしない（できない）
- 用途：DNS、動画ストリーミング、VoIP、オンラインゲーム、実IP保持、最速の素通し

## よくある疑問

### Q. 内部通信なら暗号化いらない（TCPでよい）のでは？

「内部＝安全」は**城と堀（perimeter security）**の古い発想です。今は**ゼロトラスト**＝「内部だからといって信頼しない」が主流。一度内部侵入されると非暗号の通信は丸見え（横移動でやられる）、クラウド内部は共有インフラ、コンプラ要件もある、という理由です。

ただし**内部HTTPS LBの本当の主役は暗号化より L7振り分け**（マイクロサービスのルーティング、カナリアデプロイ）。判断軸は「L7の賢い振り分けが要るか？」＋「内部通信も暗号化する要件があるか？」。両方Noなら内部L4で十分です。

### Q. ゼロトラストならTCP/UDPは使わなくなる？

なりません。**HTTPSの土台はTCP**ですし、**HTTP/3はUDPの上の暗号化通信（QUIC）**です。減るのは「**暗号化なしの素通し**」だけ。

むしろ **mTLS（アプリ同士が暗号化）+ L4パススルー** はゼロトラストの王道構成（Istio等のサービスメッシュ）。暗号化を**LBがやるか／アプリがやるか**の選択になるだけです。

### Q. SQLやSMTPも振り分けられるって聞いたけど？

「振り分け」には2つの意味があります。

- **① 負荷分散**（接続を複数backendに散らす）→ SQL/SMTPも**できる**（TCP/SSLプロキシで）
- **② 中身ルーティング**（SELECTはレプリカへ、メール宛先で仕分け）→ GCP LBには**できない**

①はGCPの話で本当。GCPドキュメントでもTCPプロキシLBの代表例にSMTPが挙がります。ただし②はProxySQL等の専用ミドルウェアの仕事で、GCPマネージドLBの範囲外です。結局「中身を読んでの振り分けはHTTPの特権」に帰着します。

## 選び方フロー（試験でも使える）

```
HTTP/HTTPS？
├ Yes → Application LB（L7・中身で振り分け）
└ No（L4）↓
    UDP を使う？
    ├ Yes → TCP/UDPネットワーク（パススルー）一択
    └ No（TCP）↓
        実IP保持 / 最速 / 素通しでいい？
        ├ Yes → TCP/UDPネットワーク（パススルー）
        └ No、プロキシの利点が欲しい↓
            TLSをLBで終端したい？
            ├ Yes → SSLプロキシ
            └ No  → TCPプロキシ
```

### キーワードのひも付け（ACE頻出）

| 要件のキーワード | 答え |
|---|---|
| URL/パス/ホストで振り分け、CDN、WAF | Application LB（L7） |
| 実クライアントIPを保持したい | パススルー（TCP/UDPネットワーク） |
| UDP を扱いたい | パススルー（TCP/UDPネットワーク） |
| 非HTTPの暗号化TCPをLBで終端したい | SSLプロキシ |
| 非HTTPのTCPをグローバル分散したい | TCPプロキシ |

## まとめ

GCPのLBは結局、**「どの深さまで中身を見るか」**で分かれます。

> **中身を読んで賢く振り分けられるのは HTTP(L7) だけ。それ以外は「接続をどう散らすか」の世界。暗号化は誰がやるか（LB or アプリ）の選択。**
